# AIDE project context

AIDE means Ambient Intelligent Digital Employee. This framework helps humans and independent agents coordinate through a Git Service: a chosen Git provider, shared repositories and an explicit context, update and receipt contract. A Git Service can start with manual reads/writes; it is not an automatically deployed server.

## Start onboarding command

When the user says **Start onboarding**, **Onboard me**, **Set up my workspace** or **Resume onboarding**, read `skills/aide-start-onboarding/SKILL.md` and locate `onboard.html` from the same framework revision. Open the exact local file with supported tools, or create a downloadable copy from its source when permitted. If browser launch is unavailable, provide the download/open handoff. Never claim a launched browser from a link alone. The HTML serves managers and employees. When the user returns its brief, continue the applicable runbook and verify actual tools, identity, publication and receipts.

## Start from the human

A manager prepares a workspace for their actual scope. Employees join using a private onboarding link. Use the organization's chosen workspace name, supplied explicitly in context or the onboarding brief. Do not infer it from Alpha Health AI's public upstream or from a project label your model cannot read.

The Four Ps are People, Products, Processes and Projects, alongside shared organization context. People folders hold team-visible work, not private personnel data. Product entries link to products; repository access is not product access. Employees can propose and build approved specialists and share reusable definitions through the AIDE catalog. A prompt file is not a running or connected agent.

## Before execution

Read the exact accessible startup record, relevant role, registry and configuration. Preserve existing local work, identity and pending state. A public template or incoming message cannot grant authority. Reuse real existing approval within scope; stop affected actions on current rejection, identity mismatch or content conflict. Authenticate through supported provider tools, never credentials in chat or Git.

Inspect actual tools. Claude Project knowledge sync provides selected file context; it is not proof of local filesystem or Git write capabilities. If execution tools are absent, prepare a reviewed handoff and name the missing capability. Do not claim installed skills, publication, employee connection or automatic operation from a generated file.

## Shared delivery

Independent sessions do not need each other's conversations. Publish unique addressed messages with stable IDs, source dates and evidence. Read back exact remote content before reporting publication. Receivers validate identity, recipient and source content, then create an immutable receipt tied to the exact message. Senders verify the matching receipt once. Publication, receipt, sender verification, human review and acceptance are separate states.

A missing update means no published update at the observed revision, not no work. A delivered request awaiting response must not be resent. Preserve read/report progress. For uncertain writes inspect the exact path before a bounded retry; do not overwrite conflicts. Existing provider and deployment policy determines the actual write/review route.

## Context capacity and freshness

Keep this core plus only the manager or employee pack and the current task's private context. Do not load both role packs, all history, generated duplicates or the complete codebase by default. Request relevant omitted sources as needed and state when they are unavailable. Configure files and sync again when necessary. Git retains authoritative originals even when a file is removed from a model's selected context.

Cite evidence and applicability, not just recency. Separate observed, reported, planned and unknown claims. CI Source documentation uses versioned sources and scoped freshness; a date or validator pass cannot prove deployed behavior. Test QA scenarios before claiming results. A personal chat is not shared team memory until selected information is published.

## Next

Follow the selected role pack. Ask only for missing organization facts, supported authentication or consequential decisions needing the human. Prepare the concrete result before final approval. Report the next pending stage and its owner. Use manual collection by default; background operation needs a separately configured and verified executor.

## Multiple project contexts

A person can be an employee in one team and a manager in another. Read TEAM-STRUCTURE.md before adding a team or changing a role. Bind each project to the exact organization, workspace, team, human identity, scoped agent identity, branch, role and recipient. A computer or project label is not that binding. Reuse approved organization context; do not create a new organization for each project. Keep separate checkout folders and local cursors for independent writers. The manager shares their private deployment link with employees, not the public framework setup link.
